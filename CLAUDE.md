# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin marketplace (`claude-sabai`, `.claude-plugin/marketplace.json`) holding **mods**: plugins built on Claude Code's function-hooks API (Claude Code ≥ 2.1.287). Each mod lives in its own folder under `plugins/`. Today there is one, `plugins/sabai`. The plan, decisions and backlog are in `docs/PLAN.md` (written in Thai).

## Commands

Run from the repo root; each mod is checked on its own folder.

```bash
claude plugin validate .claude-plugin/marketplace.json   # marketplace manifest
claude plugin validate plugins/sabai                # manifest + what the hooks module hooks/calls, and anything the engine would refuse
claude plugin test plugins/sabai                    # runs every *.test.ts(x) under the folder (no per-test filter)
tsc -p plugins/sabai                                 # type-check; needs the engine-laid types (see below)
claude --plugin-dir plugins/sabai                    # run the mod in a session; saving a file hot-reloads it
bash statusline/hub.test.sh                          # the terminal status line's tests (HUB_BASH=/bin/bash for macOS's bash 3.2)
git config core.hooksPath .githooks                       # once per clone: pre-commit validates, type-checks and tests
```

- `plugins/sabai/tsconfig.json` extends `.claude-plugin/types/tsconfig.json`, which Claude Code writes beside a mod only after it has loaded it (hot reload or `--plugin-dir`). That folder is gitignored and absent on a fresh clone, so `tsc` works only after one load. CI (`.github/workflows/check.yml`) therefore only validates and tests; the pre-commit hook type-checks when the types exist.
- The API reference is that laid file, `.claude-plugin/types/claude-code/index.d.ts` (~14k lines, every event, `$` noun and element prop). Grep it rather than guessing an API.

## Dev and production installs on the owner's machine

An installed plugin runs from a copy in `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, re-copied only when the version changes: `/reload-plugins` reloads that copy, not the repo. So the machine keeps two channels apart:

- **Production**: the `claude-sabai` marketplace comes from GitHub (`claude plugin marketplace add panupat-top/claude-sabai`), as users install it. After a release is merged and pushed, `claude plugin marketplace update claude-sabai` then `claude plugin update sabai@claude-sabai`.
- **Dev**: `~/.claude/settings.json` sets `"env": { "CLAUDE_CODE_PLUGIN_DIRS": "<repo>/plugins/sabai" }`. Every session, the desktop Code tab included, then loads the checked-out branch in place as `sabai@inline`, which silently wins over the installed copy; a save reloads it. The env is read when a session starts, so a change to it needs a new session.
- `claude plugin list` shows which is loaded (`sabai@inline` with a path is dev). To see a release as users get it, remove the env line, open a new session, then put it back.
- To preview a drawing outside the engine, show each SVG as its own `<img>` (a data URI): inline SVGs in one HTML page share their `<style>` rules, so class colours leak between skins.

## sabai architecture

A band above the prompt (comfortable: three panels — Clawd large with his mood, a reason and his tricks, the info row with the usage limits in one of four styles filling the band's height, and a race box where Main and each subagent run a lane while work runs; compact and narrow: stacked rows with the live strip and crew; a top row above it holds the info row at the left and the toolbar as Lucide icons at the right), two panes (agents, in three boxes: Now, the crew at work as a timeline and a lane for Main and each agent; Viewing, the run viewed; Earlier, the crews before; settings, most seen first: the look (layout, raised or flat cards, bar style, the rows without choices of their own), the usage (style and limits), the info row's parts, Clawd's extras, agents, chat, the guard, notifications, reset; a part with choices has its On/Off in its group's head; the layout, cards and usage style are drawn choices (`densityPreview`, `skinPreview`, `usageSketch`, each a sketch over its Button), and the bars, info row and chat show samples), and touches to the conversation (tool calls drawn as one-line steps, test results, callouts, Thai spinner words, a receipt under each working turn). Clawd shows the session's mood in the band. The mod is the desktop Code tab's alone: a terminal or `-p` session is left as Claude Code draws it, with no reads, commands, tool, prompt section, guard or notifications.

- **Desktop only.** `session.start` sets the mod up (`setUp`: saved choices, commands, the step tool, the clocks, the git and node reads) when `$.session.surfaces()` holds `desktop`, else `session.attach` does when the desktop attaches (an SDK session such as the Code tab's starts drawing nowhere, and the desktop attaches on its first ask to draw), and failing both the band's first desktop draw does (from `$.clock.after`); `setUp` sets the module's `desktop` flag, and every engine-event hook passes straight through (`return next(e)`) while it is off. Render hooks pass through on any `e.surface` but `desktop`, so a terminal attached to the same session sees the engine's own rows.
- `hooks/register.tsx` is the only module that touches `$`. It hooks engine events (`session.start`, `session.attach`, `session.measure`, `tool.call` on `TaskCreate`/`TaskUpdate`/`TodoWrite`/`Edit`/`Write`/`Bash`/`Read`/`Monitor`/`TaskStop` and, with no matcher, every subagent call and the step tool, `tool.check`, `agent.spawn`, `turn.step`, `turn.complete`, `turn.start`, `prompt.compose`, `prompt.submit`, `classic.SessionStart`), writes state, registers `/sabai-settings` and `/sabai-agents`, and renders `AbovePrompt` (the band), `Pane` (agents, settings) and the conversation rows `ToolUse`, `ToolGroup`, `AssistantMessage` and `Spinner`.
- **The turn log and the guard.** `turn.start` empties a `turnLog` atom; `tool.call` hooks on Edit/Write/Bash fold the main turn's calls into it (`logged`), and `turn.complete` files the log under the turn's answer in `receipts`; the `AssistantMessage` row whose text is that answer draws the receipt line (`receiptSvg`) under itself. A turn with no answer of its own returns `receiptText` as its text, a notice under it. The guard blocks in `tool.call` and asks in `tool.check` (`{ decision: 'ask', reason }`), per rule as `prefs.guardRules` says; its `tool.call` and `tool.check` hooks carry a `.catch` that refuses (`failClosed`), since a failed hook is skipped and its call would run. Each catch counts in `guardCaught` and stamps the log, so Clawd startles.
- **The agents pane.** Each `AgentRun` carries what its detail shows: `agent.spawn` sets its `crew` (the main turn's `turn:<start>`, its workflow's `wf:<runId>`, or its parent's), `brief` and `background`; `turn.step` adds every request's new tokens (input, cache writes, output; not its cache reads) to `spent`; the `tool.call` hook with no matcher logs each subagent call through `logAgentCall` (in flight in `doing`, then `calls` with its time and outcome, `tools` counted, `files` read or changed with lines from `logged`), and runs a tool the race's own hooks leave out in the agent's lane, so the band and the pane count alike; the step tool keeps its `notes`. A finished agent sent more work runs again in the crew at work, its report kept in `rounds`. `crewsOf`/`openCrews` give the crews at work (shown in full) and the earlier ones (a line each in a foldable box, by day when they span more than one); `spawned` keeps the newest `CREWS_KEPT` crews. `agentMood` and `thaiLine` say how each agent stands. The main loop's turns are runs too, in their own `mains` atom so the band, race and toolbar (which read `agents`) never see them: `turn.start` opens one (`main:<start>`, closing the one before), `turn.step` and the same `tool.call` hook (`logAgentCall` with `main`, no race of its own) fill it, `turn.complete` ends it with Claude's answer as its report; the pane sets each before its crew's first agent, drops a finished one that called nothing and started no agent, and keeps older ones only where their crew had agents. Viewing shows the run viewed (View on its lane toggles it, Close shuts it; none at first), else an invitation and `needsLook`'s agent; its parts are unboxed titles over their drawings. When an agent finishes with a report and Thai summary is on, `summarize` asks Haiku (`$.model.complete`) for Thai bullets, `summary: 'pending'` meanwhile; no answer leaves none. The pane spends `PANE_BUDGET` on its drawings, each costing its escaped source and its alt, in order (overview, detail, earlier lines, lanes), and counts the lanes that do not fit. Clear keeps the crews the pane shows in full, Main's and the agents' alike.
- **State** lives in `$.state` atoms declared in the contract `types/index.d.ts` (`interface PluginState['sabai']`); a draw `read`s them and redraws when an `update` writes. `now` is written every 30 s, and every second while the main turn or an agent works (the live clocks), so the band is redrawn once a second during work. Module variables (e.g. `cwd`, `desktop`) are only for things `session.start` re-sets, since a reload starts the module over. The chosen skin is also persisted with `$.store`.
- **The band's layout.** `bandSvg(p, list, W, opts: BandOpts)` draws the stacked band (compact draws its usage with `usagePart` at `USAGE_MIN_H`; the comfortable band below 480 px keeps two-line cards, `cardsPart`), or with `opts.hero` (comfortable density, W ≥ 480) `heroBand`: the Clawd panel (his headline from `MOOD_WORDS`, the `moodLine` reason, his `trickOf` trick), the middle (the live strip and tasks; then `usagePart` in `prefs.usageStyle`: tiles, rings, columns or rows) and, from 760 px, `racePart`; below 760 the live strip and crew rows stay in the middle. The band carries no info row: the top row above it holds `infoSvg` (`infoPart`: the project, a branch tag with sync counts, then git user and Node in the muted ink, every chip packed from the left on a card of the band's colour that fills the room the icons leave, `W` less `TOOL_CHIP` per icon; Node at its full version; Clawd leads it in the stacked band when no tasks row or live strip holds him) and, at its right, the guard as a green `shield-check` (`toolIconSvg('guard', …, 'ok')`, pressed it opens the settings) then the toolbar as `toolIconSvg` icons (compact while the surface offers it, agents, settings; a count and the warn, alert or clay ink drawn in, the colour on one at a time). Each icon is a tile of the card as tall as the info row, its Lucide shape a mask over a rect in a fill class (`m`, `c-warn`, …), so the skin's stylesheet colours it; the row has no column gap, so it reads as one strip. The band's height is the tallest of Clawd's panel (112 px), the race and the rows above the usage plus 50 px; the usage fills what is left. Until the session has read, the band is a still skeleton of the same height: `usage` is `null` until the engine answers (then `meters` gives `pending` meters drawn as an empty track and a dash), and the info row draws two bars until `env.read`; an answer with nothing to show leaves `usageNote` in the usage's place. The race's state is the `race` atom (`RaceLog`: each member's tiles, call `count`, call in flight, latest call's name `said` (written by `stepping`), `failed` calls, last fall and score, and the turn's `total` and `fails`), written by the Read/Edit/Write/Bash hooks through `racing` and laid out by `raceOf`, which shows nothing without agents (the live strip tells Main alone), names lanes by the agent's description, steps them by their plan's step or else their latest call, merges agents of one type when more run than three lanes hold (summing their counts; shared lanes first, so a merged type is never the one left out), gives each agent its `agentMood`, `quietMs` while quiet and `fresh` for `FINISH_MS` after it finished, and tells Main `thinking` (working, no call in flight) from `waiting` (not working). `racePart` draws a 22 px row per lane: a mood stripe, the Clawd (Main in the captain's cap) at `RACE_SCALE` as paths, name and step, then `✗` failures, a plan's done/total and bar, and the time; a fresh finish flashes its row with confetti, then folds to a check, a fresh failure (`out`) falls on a red-flashing row, then folds to a cross, and a stopped agent folds to a hand, each `statusMark`'s badge (the crew row's too). In the pane, `endBadge` puts the same ✓/✗/✋ badge on an ended lane's Clawd and flashes the lane for `HOP_MS` after it ends, while its Clawd hops or falls. Main is named so in the race and the pane, in the captain's cap. The main turn's start and step are `turnStartedAt`/`liveStep`. `background` holds the ids of the background tasks the main conversation started: a Bash call's `backgroundTaskId` (asked for, Ctrl+B or a timeout) and a Monitor's `taskId` add one, `TaskStop`'s `task_id` and a `prompt.submit` from a `task-notification` (`endedTasks`: each block with a status other than running) take it away; while it is the person's turn, `N running` after a pulsing dot takes Clawd's line in the comfortable band. The live strip (`livePart`) shows the step in flight as its kind's tile (`kindTile`, blinking) with its words and its own time (`liveStep.at`), or three blinking dots and `thinking`; at the right the main turn's tiles from the race log (`calls.main`, the last `RACE_TILES`, with `+N` for the earlier `count`), the lines its edits changed (`turnLog.files`) and its tests; below 260 px of room the step keeps it and the lines and tests go. `prefs.extras` turns Clawd's accessories and tricks off. The race's CSS rides inside its own box so other drawings stay small.
- **Pure logic** — `model.ts` (meters with levels, chips, task reducers, formatting, `moodOf`, `moodLine`, `trickOf`, `resetClock`, `accessoryOf`, `raced`, `paceOf`), `agents.ts` (subagent run reducers and their call log, `progressOf`, `raceOf`, type styles, crews, `agentMood`, `thaiLine`, the summary's prompt and reading), `chat.ts` (tool summary lines, `actOf` for a subagent's call, test-output parsers, callout splitting, spinner words, the turn log's `logged` and `receiptText`), `themes.ts` (the two looks' keys and names, `contrast`), `guard.ts` (`riskOf`, `GUARD_RULES`, the commands the guard catches) — takes plain values and is unit-tested directly.
- **Drawing** — `svg.ts` builds the desktop SVGs (`bandSvg`; the agents pane's `crewSvg`, `laneSvg`, `agentHeadSvg`, `toolsSvg`, `stepsSvg`, `activitySvg`, `filesSvg`, `earlierSvg`) from a `Look` (`lookOf(skin)`: stylesheet, bar colours, pill, Clawd tint). There are two looks, each with light and dark inks in one stylesheet (`twoModes`): `raised` (the default; `RAISED_CARD`/`RAISED_TEXT`, white cards in light, #2d2d2b in dark) and `auto`, shown as Flat (`CARD`/`TEXT`, cards a shade off the surface); a stored name not in `SKINS` (an older version's skin) is ignored at load, so the band starts raised. No look paints a background, so the band sits on the surface. Small drawings redrawn often (toolbar icons, the info card) carry only their classes' rules (`leanCss`), and a call is a tile (`kindTile`) of its kind's Lucide icon (`CALL_ICON`), placed with `<use>` from defs the drawing carries once (`iconDefs`). Statuses and call kinds take one pastel palette (`PALETTE`: per hue a tile ground `kb`, its glyph `kf` and lines and bars `kl`, light and dark), painted as `var(--kb-ok)` and so on and declared per drawing for the variables it uses (`paletteCss`); a glyph reads at 5:1 on its ground (the theme test); `sprites.ts` holds pixel sprites and their CSS animations; `icons.ts` holds the info-row marks (Octicons / Simple Icons path data), and `strokes.ts` the chat's Lucide stroke icons (animated by CSS in `svg.ts`), generated once from Lucide's files.

## Engine constraints that shape the code

- A render tree (a band or a pane) must stay under 100,000 characters serialized, or nothing of it is drawn ("Nothing to show yet" in a pane). A Clawd sprite alone is ~14k.

- `$` cannot be passed across an import: any helper taking `$` must be declared in `register.tsx` itself.
- `read`/`update` must name their atom where they are called (an atom const of the file, or `memberOf` of one): an atom passed in a variable makes the module fail to load, since the engine lists a module's state by reading the calls. Choose between atoms with a branch (`updateRuns`).
- Branch a render hook on `e.surface !== 'desktop'` (then `next(e)`): it also narrows `$.ui.resolve(e)` to the desktop's table, which has `Svg`. The terminal's table lists `Svg` too but cannot draw it.
- The desktop draws an `Svg` as an image. In a column its siblings take new lines; in a `Box flexDirection="row"` it sits beside `Button`s and `Markdown`s (checked on the desktop), which is how the top row puts the info row's own SVG (`infoSvg`, packed from the left and as wide as it draws) beside the toolbar's icons. With no `width` prop the surface fits the markup to the slot: a wider one is scaled down, hence drawing at `bodyColumns × 8.25`, and in a pane a narrower one is stretched up to the pane's width (the settings' 320 px bar sample was), so a drawing meant to keep its size passes `width` and `height`. Svg width/height must be 1–4096 px and its source ≤ 131,072 characters; clip-path ids must be unique (`sabai-*`).
- The desktop draws a `Button` as a native button from its `label` alone (children, colours and `hover` are ignored; a `hotkey` shows as a keycap), and a `Button` holding an `Svg` is refused (the whole hook is skipped). Put what the desktop should show in `label`. A clickable icon is a `Markdown` whose text is an image link, `[![alt](data:image/svg+xml;base64,…)](https://sabai.invalid/<kind>)`, answered by `onLinkPress` (no browser opens; checked on the desktop): one Markdown per icon in a row Box sits side by side, while several in one Markdown stack, and a `file:` image is not drawn. A large image link (a 220 px sketch) took presses unreliably on the desktop, so the settings' sketches sit over Buttons rather than being links; in the agents pane an image link took no presses at all, even at the toolbar's size (a lane's eye, 30×24), so lanes keep their View Button. Of the common commands the Code tab offers `/clear` and `/compact`, not `/rewind` or `/resume`.
- A pane `Svg` keyed the same while it comes to show another subject (the agents detail switching agents) kept its old image on the desktop: key such drawings by their subject (`detail-calls-${id}`).
- SVG animations: the desktop draws each drawing as an image and redraws the agents pane every second while an agent runs, restarting its animations. Keep loops ≤ 1s, and start every animation from a visible frame (an image can sit on its first frame); a `stroke-dashoffset` draw-in never runs there, so use transforms or opacity.
- Native `Text`, `Button` and `Markdown` keep the surface's own ink, which follows the OS light/dark theme; `Button` and `Markdown` take no colour. Never put them on a fixed skin colour (a `Box` `backgroundColor`): the ink may not read on it.
- The desktop raises no `classic.*` event to a hooks module (checked with a `*` logger: the engine's own events arrive, no `classic.Stop`, `classic.PreToolUse` or `classic.SessionStart`), so what a classic hook's input alone carries (`Stop`'s `background_tasks`) is out of reach there; take it from the engine's events and tool results.
- `session.measure` only fires on the next API response, so `session.start` reads `$.session.usage()` itself.
- Work started from a button press is cancelled when the press ends; run it via `$.clock.after`.
- In the desktop Code tab `$.ui.status` is not shown and `/config` is unavailable, so settings are slash commands.
- A drawn tree's size depends on the drawings in it: the agents pane draws its parts by their drawn size (`PANE_BUDGET`; its drawings carry only the inks, motion and faces they use, and its Clawds as paths), and repeated marks (dither dots, ticks) are capped so a very wide band stays inside the limits.
- Conversation rows: a `ui.render` hook on `ToolUse`, `AssistantMessage`, `UserMessage` or `ToolGroup` replaces the row, and a tree wrapping `await next(e)` keeps the engine's row with ours under it (both checked on the desktop). Round borders and `Text` colours are honoured there; an `Svg` is drawn as an image and, without `width`/`height` props, stretched to the row's full width, so chat drawings are fixed-size and pass both. The desktop always draws its own `ToolGroup` line and the thinking summary, and shows no `SessionMode` footer, so the guard label lives in the band's info row. Transcript `Text`/`Box` colours are theme keys (`success`, `error`, …), since the conversation follows the person's theme, not the skin. A standalone tool row's `output` is often absent on the desktop (its result is a separate `ToolResult`), so steps fall back to the call's input. Bash durations are a `StateFamily` keyed by `tool_use_id` (read with `memberOf(atom, e)`), so a new call redraws only its own row; a call that opened the permission dialog (`classic.PermissionRequest`) shows no time, while the auto-mode classifier's `ask` keeps it.
- Turn ends and permissions (checked on the desktop): `turn.complete` returning `{ text }` keeps the answer and draws the text as plain text in a folded "Claude Code notice" under it, prefixed with the names of the plugins hooking it. An event registered twice without a matcher is refused at load, so a feature extends the existing hook. `classic.PreToolUse` answering `{ ask }` opens no dialog; `tool.check` answering `{ decision: 'ask', reason }` opens the permission dialog with the reason in default mode, while in auto mode the ask goes to the classifier, which may allow it. Neither hook sees the permission mode. An SVG drawing follows the OS's light/dark switch live, both through a class set inside `@media (prefers-color-scheme: dark)` and through a CSS custom property used as a `fill="var(--x)"` attribute (checked on the desktop). A `ToolGroup` row starts folded; `isExpanded: true` unfolds it into its steps. An `AssistantMessage` carries no turn id, but the final reply's `text` equals `turn.complete`'s `answer`, which is how the receipt finds its reply.
- Everything the band shows must come from the engine or the project's own `git`/`node`; values that cannot be read are hidden, never faked. No credentials or external files.

## The terminal status line (`statusline/`)

`hub.sh` is a Claude Code `statusLine` command for terminal sessions, which sabai leaves alone: two lines (folder, branch and sync, model, effort, cost, time; then context, 5H and 7D line bars with their resets), each part led by a Nerd Font v3 icon from its Material Design range (U+F0000 up, the same code points as the `@mdi/font` webfont, so a browser preview can draw them), written as literal glyphs since bash 3.2 has no `\U` escapes; `SABAI_HUB_ICONS=0` drops them. It is not part of the mod and has its own version in its header. It runs on every status refresh, so it keeps to one `jq` (all fields joined by `\x1f`, since tabs collapse empty fields), one `git status --porcelain=v2 --branch`, and helpers that write with `printf -v` instead of forking `$(…)`; about 35 ms against the old script's 300. It must run on macOS's bash 3.2 (no `${x^^}`, no associative arrays; a substring counts bytes, so join with `${s:+ · }` rather than cutting a multibyte separator off). Colours are the terminal's 16 ANSI ones so it follows the person's theme. `HUB_NOW` pins the clock for the tests.

## Conventions

- `README.md` is for people installing and using the mods (what it is, install, commands, privacy, troubleshooting). Development notes belong here; the roadmap and decisions in `docs/PLAN.md`.
- Code, comments, commit messages and repo docs are in English; `docs/PLAN.md` is in Thai.
- A release bumps the mod's `version` in both `plugins/<mod>/.claude-plugin/plugin.json` and its entry in `.claude-plugin/marketplace.json`, and updates the README if commands or behaviour changed.
- Before committing, run validate, test and `tsc` (the pre-commit hook does all three). Commit messages: an imperative subject line, then a short bullet list of what changed.
- User-visible text in the band and pane is English. By the owner's choice the exceptions are Thai: the spinner words, the agents pane's lines for each agent's mood (`thaiLine`) and its summary (the counted facts and Haiku's bullets). Keep every text colour at ≥ 4.5:1 on its card, in light and dark; the theme test enforces it for both looks.

## Tests

Tests import `test`, `expect`, `mock` from `claude-code/testing`. In a test, `$` is the engine's (it has no `env`, `settings`, `store` or `fs` nouns), and hooks registered with the test's `on` sit beneath the plugin and stand in for the engine — e.g. `process.run`, `session.usage`, `store.get` answered as `{ value }`, while object-result events like `session.start` return the object directly. UI is checked by `$.ui.mount({ plugin, surface, component, requestId, props })` and `findAll` on the `desktop` surface; the test engine answers `session.surfaces` (`['desktop']` unless a test says otherwise), and one test checks that a terminal session is left alone. Contrast of both looks' text colours, light and dark, is asserted (≥ 4.5:1) in `tests/themes.test.ts`.
